# 在 Kimi Code 的帮忙下，我把 Tavily 的搜索额度薅成了一个池子

> 本来是怕搜索额度用完麻烦，结果在 Kimi Code 的陪伴下，硬是薅出了一个自托管的搜索代理池。
> 现在好了，再也不怕哪个工具搜索额度见底了。

---

## 开头：先说清楚我为啥要薅这个羊毛

我手头一堆 AI 工具都要用搜索。你可能觉得搜索有啥好稀罕的，但真用起来就知道，
额度这玩意儿，说没就没。

- **Kimi Code** 自己有搜索，但它额度用光了之后，搜索服务跟着一起没——想查个东西都查不了。
- **Tavily** 的搜索质量不错，而且每个月白送 1000 次，说实话挺大方。但架不住我天天用，
  加上 Kimi Code 那边时不时要靠它顶上，1000 次看着多，用着用着就见底了。

这时候我发现一个事：**Tavily 官方是允许你注册多个账号的。** 一个账号一份额度，
那我就多注册几个呗，把每个账号的 API key 都收过来。

但 key 多了又有新麻烦：**一个工具用到额度上限，手动去换 key 特别烦。**
你正聊着天呢，突然搜索挂了，得去后台翻 key、改配置、再试——一来一回，思路全断了。

于是我就想：干脆做个**池子**，把这些 key 都扔进去，让它自己轮着用。
哪个 key 额度多就用哪个，满了自动换下一个，我啥都不用管。
**这个池子，就是 tavily-proxy。**

而整个薅羊毛工程，是在 Kimi Code 的帮助下搞定的。这篇就讲讲，我是怎么薅的。

---

## 第一步：薅羊毛也得有规划，先让 Kimi Code 给个思路

薅归薅，不能瞎薅。我先把想法丢给 Kimi Code：我想把多个 Tavily 账号的 key 攒成池子，
自动轮换、额度高的优先，你看这事儿怎么干？

它没急着甩代码，先给我抛了几个要想清楚的问题：

> 你是要把请求转发给官方 MCP，还是自己直接调 Tavily 的接口？
> 「额度还剩多少」这个数，从哪来？配置死数字，还是去调它的接口？
> 多个 key 之间到底怎么选？

当时我还嫌它啰嗦——薅个羊毛而已，问这么多。后来证明，**这几个问题全问在点子上了**，
尤其是第二个，让我少走了一个大弯路（下面说）。

---

## 第二步：调研，重点是「实测」，别信文档

### 直连接口，别桥接官方 MCP

第一个问题其实很快定了：**别桥接官方 MCP，自己直接调 `api.tavily.com` 的 REST。**
为啥？因为我要看每个 key 到底花了多少 credits——REST 接口响应里能带 `include_usage` 返回
这个数，官方 MCP 桥接拿不到。选路全靠这个数，拿不到还选个啥。

### 差点白薅：同一账号的多个 key，额度是共享的！

第二个问题才是大坑。想知道「额度剩多少」，得调 Tavily 的 `GET /usage` 接口——但这玩意儿
**官方没文档**，是个隐藏接口。Kimi Code 说，没文档就没文档，直接调一下看看它返回啥。

一测，傻眼了。返回结构是 `{key: {...}, account: {plan_usage, plan_limit, ...}}`，
`key.limit` 基本是 null，真正的额度在 **account** 那一层。

翻译成人话：**Tavily 是按账号算额度的，同一个账号底下挂再多个 key，共享同一份额度！**

也就是说，我本来以为「多注册几个 key = 额度翻倍」，实际是**白开心**——多开几个 key 只能
缓解每分钟的限流，总额度一分没多。真正的羊毛在**账号**层面：多注册几个**账号**，那才是
实打实的额度叠加。

这个坑要不是实测，会一直埋在我的选路逻辑里，还自以为薅到了。Kimi Code 顺手还发现这接口
有隐性限流（大概 10 次/10 分钟），所以轮询别太勤，60 秒一次刚刚好。

---

## 第三步：开薅——按票拆着干，一票一个闭环

规划清楚了，开干。项目拆成 11 个票，一票一个闭环：规格 → 测试 → 实现 → 提交。

1. 工程骨架（Rust + axum + SQLite，CI 就绪）
2. 登录认证（单用户，argon2id）
3. 上游密钥池管理（一堆 `tvly-` key 的增删改查）
4. 额度记账（拉 usage + 记 credits）
5. 代理密钥管理（给客户端发 `tp-` key，随时能吊销）
6. MCP 端点（`POST /mcp`，`tavily_search` 直转）
7. 选路器 + 状态机（三个健康状态 + 按额度选路）
8. extract / crawl / map 三个同步工具
9. research 长任务编排
10. 请求日志 + 统计看板（留 30 天）
11. 部署管线（编译静态二进制 + 推 GHCR）

每票都先写规格再写测试再写实现，看着慢，实际稳。

### 状态机：分支多到晕，先写测试压压惊

每个 key 有三个健康状态：**冷却**（429 限流，歇 60 秒自动回来）、**耗尽**（432/433 额度见底，
等到计费周期重置才复活）、**禁用**（401 废了或者我手动拉黑，得人工处理）。

加上「额度多的优先选」，分支组合一大堆。Kimi Code 的招数是**先写测试把每个分支都钉死，
再补实现**：冷却到期能不能自动回来、耗尽到点能不能复活、禁用是不是非得人工——全有测试兜着。
黑盒测试用 mock 上游，不需要真实 key，CI 里随便跑。

### MCP 协议：能自己写就不引框架

MCP 的 Streamable HTTP，一开始想用现成的 Rust 框架。Kimi Code 一测发现：这协议的无状态形态
特小（就一个 POST + JSON 响应，连会话 ID 都没有），**手写 JSON-RPC 分发比引框架还省事**。
最后把 `rmcp` 那套从清单里划掉了——依赖少一个是一个，最后的镜像直接 `FROM scratch`，
小得可怜。

---

## 第四步：薅到的羊毛，得打理得顺手

池子跑起来了，后面全是「让它好用」的活：

- **密钥明文可见 + 一键复制**：加 key、发 key 都利索了
- **吊销改成删除**：列表里不显示已吊销的，干净
- **MCP 集成链接**：配好样式，复制即用
- **中文看板**：哪个 key 健康、哪个在冷却、请求成功率多少、延迟多少，一眼看全

UI 这摊子事，Kimi Code 也是看图说话——我截个图说「这儿不对劲」，它改完我再截，
来回几次就顺眼了，不用我掰开揉碎讲。

---

## 第五步：连开源都是顺手的事

池子稳定了，寻思着这么好玩的东西不能自己藏着，开源吧。这回也是先问 Kimi Code
「开源该准备些啥」，它给清单，我们照做：

- README 写成给外人看的（连我自己那套生产部署的东西都从 README 里删干净了）
- MIT LICENSE、CONTRIBUTING、SECURITY、行为准则、issue/PR 模板
- GitHub Actions：测试 + 编译静态二进制 + 推 GHCR 镜像
- 根目录放个 `compose.yaml`，别人 `docker compose up -d` 就能薅

`github.com/ijkzen/tavily-proxy` 就这么开源了，镜像在 `ghcr.io/ijkzen/tavily-proxy`。

## 最后：这个羊毛薅得值

现在这池子跑得好好的：多个账号的 key 堆在池子里，哪个额度多就用哪个，限流了自动歇会，
额度见底了自动换下一个，实在不行还有状态机兜着。**我再也没为「哪个工具搜索额度用完」发过愁。**

总结一下 Kimi Code 到底帮了我啥：

1. **动手前先问「怎么办」**——它给的三个问题，全是决策点，让我没瞎薅。
2. **没文档的接口，直接实测**——那个「按账号共享额度」的真相，是测出来的，
   差点白薅一场的坑就这么避开了。
3. **先测试后实现**——状态机分支那么多，没有测试兜底我根本不敢动。
4. **能少依赖就少依赖**——MCP 协议手写，换来一个 `FROM scratch` 的迷你镜像。
5. **开源也是一套流程**——README、LICENSE、CI、compose，照着清单一步步来就行。

最爽的是啥？整个过程不是我求着它写代码，而是**它陪着我一个个想清楚、测明白、做稳当**，
最后薅到手的羊毛，实打实是自己的。
